# 多人协作代码重构计划 v0.2

日期：2026-10-29。基线：main / ca7ebb2。状态：供团队认领的提案；本次没有修改运行代码，没有创建分支、worktree或提交本计划。

## 一、结论与范围

需要重构，优先解决多人同时触碰共享入口的问题。按功能拆模块，再配置负责人；保留现有微信小游戏、CommonJS、自绘Canvas和存档结构。已有board、match3、wave、meta、save等边界继续沿用。

重点：render.js约300KB、main.js约110KB、combat.js约203KB、config.js约103KB。文件体积只是风险信号；目标是让美术换动画、界面改卡片、工程改奖励不必同时编辑主文件。

不一次性重写，不为四个人建立四套平行架构，不趁搬文件调整玩法和数值。纯迁移与功能修复分提交。

## 二、目标边界与建议职责

| 边界 | 建议负责人 | 可独立修改 | 禁止跨层副作用 |
|---|---|---|---|
| 页面和弹层 | W工程师/美工 | 菜单、技能配置、结算、图鉴、商店布局与命中区域 | 绘制不得扣款、发奖、变更装备 |
| 图标和特效 | D美工/工程师 | 图标、帧清单、锚点、时间轴、播放和回退 | 动画不得决定伤害是否发生 |

| 规则与数值 | W策划/美工 | 规格、参数表、反馈规范和验收场景 | 迁移期间不直接改散落的计算式 |

这是建议，不表示成员已经认领；先核对他们当前任务再分配。每模块一名当批负责人，其他人通过协作分支修改并由其评审。

## 三、拟议目录与迁移原则

```text
js/
  config.js                         # 兼容出口，渐进组合分类配置
  skills/
    global-catalog.js               # 16项定义、文案、颜色、可调参数
    global-loadout.js               # 双槽校验、互换、旧档兼容
    global-runtime.js               # 效果施放、时长、波末清理、一次性标记
  global-skills.js                   # 暂保留原get/slots/tick/cast接口的兼容出口
  config/
    economy.js                     # 后续触碰时迁移
    fields.js
  game/
    main.js                         # 初始化、状态转换、帧循环、协调
    render.js                       # 保留Renderer入口，转调子模块
    input/menu-actions.js           # 菜单动作路由，保留命中顺序
    screens/skill-loadout.js
    screens/settlement.js
    screens/menu.js                 # 后续按需要拆图鉴/商店
    icons/skills.js
    icons/special-blocks.js
    fx/manifest.js
    fx/frame-player.js
```

只创建本批实际迁移文件。第一阶段保留Renderer实例及原方法签名，子模块使用显式依赖；避免复制上下文常量或大量bind，避免在目录间循环require。main仍持有游戏实例，但用小接口传递数据，逐步降低对整个game对象的依赖。

## 五、接口先约定再迁移

### 页面

render读取显示数据，生成显示和命中区域；action处理购买、解锁、装备。第一步可以沿用push(key,data,x,y,w,h)，稳定后再统一类型。卡片绘制、实际命中和分页必须用同一布局计算，不能三处硬编码。

### 双槽全局技能

对外使用slotIndex(0/1)和skillId，充能存储与技能ID分开。当前shuffleAmmo/refillAmmo仍兼作左右槽充能，名称易误导：先在内部加索引适配，后续统一命名；保留原字段兼容测试和飞光反馈。禁止简单全局替换。

定义效果上下文：塔、敌人、城墙、棋盘操作、特效反馈与随机源。明确战斗时间推进、暂停冻结、波末清盾、重开清状态、无目标是否消耗的规则。文档未定项列出，不在机械迁移时暗改。

技能目录作为显示文案和参数的共同来源，逐步消除“说明写8、实际消耗或收益读取另一套值”的风险。当前首版的反伤覆盖范围、共鸣遇到无周期技、双子遇到连锁四消、齐射遇到多弹道技能等需要专项验收。

### 动画与战斗

逻辑决定伤害时间和范围；动画只消费特效记录。锚点、帧时间、混合与资源回退进manifest。新增素材仍放assets分包；不要把原始美术目录加入上传包。

### 随机与测试

候选、技能目标、反应随机选择逐步使用可注入随机源；先记录现状，再改确定性。测试既检查状态，也检查真实调用链，不能只验证mock返回值。

## 六、防冲突工作流程

1. 每人独立分支和工作目录/worktree；不用同一个有未提交修改的目录并行写。另一个聊天不是另一个工作目录。
2. 使用任务登记：任务ID、基准提交、负责人、涉及文件、接口变化、预计集成顺序、待验收项。
3. main/render/config为共享入口：每批一名集成人；成员在新模块完成实现，提交接入说明。旧实现删除由集成人统一执行。
4. 同一职责的文件迁移期间短暂冻结功能改动；其他模块继续开发。不要全项目停工。
5. 一次提交一个可回退切片；先搬移保持行为，再修缺陷，再做新机制。回退不删除他人文件。
6. 每次合入只运行相关检查；新改动或失败才扩测。完成的批次更新任务表和变更记录。
7. 不自动处理当前文档删除和未跟踪美术；由原负责人确认是否保留/提交。
