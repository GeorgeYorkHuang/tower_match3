# 战斗性能排查与首轮优化

日期：2026-11-09。针对真机在 20 波之后持续发热的问题。

## 已确认的热点

1. `js/game/fx/approved-fire.js` 的燃烧区域按 `round(πr²/100)` 个小火苗绘制，每帧重新创建位置数组、计算三角函数并排序。半径 60/80/100/130/180 分别绘制 113/201/314/531/1018 次，多个地面区域直接叠加。
2. `js/game/fx/approved-debuffs.js` 的状态图按怪物精灵帧、状态、动画相位缓存。缓存未命中时，同步创建特效实例、从零模拟几十步、合成 128×128 像素并上传新画布。160 张缓存不足以覆盖后期组合，淘汰后反复重建；一次冷合成在桌面测试中约 0.5–7.5ms，并非手机数据。
3. 怪物提亮与精英扫光重绘本体时，会再次绘制状态特效，造成额外叠加、缓存访问和绘制。

## 实装

- 使用原 `fire-approved/ring-flame.png` 合成 `fire-approved/ground-patch.png`，40 帧、20fps、2 秒循环、256×256 单帧。每个地面区域每帧只画一次；按真实半径缩放、保留淡出及战斗时钟，种子用于错开动画相位。火苗密度以半径 100 的标准贴图统一缩放，因此不同半径下火苗大小会随区域缩放。图集约 670KiB，解码约 10MiB。不修改地面实体或伤害范围；图集未就绪仍用原轻量回退。
- 状态合成改成有上限的 FIFO 队列，每帧最多读回一个新轮廓、合成一个状态帧。缓存命中直接画图；新相位未就绪时复用同轮廓、同状态的缓存，新状态显示轻量提示。繁忙时状态粒子的动画更新会降低，但状态图标、命中反馈立即显示；状态时长由战斗逻辑照常推进。
- 每份轮廓只读回一次像素，冰缓染色复用该批数据；合成缓冲重复利用，160 个状态图画布填满后循环使用。轮廓最多 96 份，请求最多 96 个；超过上限不挤掉正在等待的请求，过期请求丢弃。
- 读回失败后本局使用轻量状态提示，避免逐怪、逐帧重试异常。重开清理轮廓、状态图、队列及临时缓冲。
- 受击提亮和精英扫光只重绘怪物本体，正常一遍状态覆盖保留。
- 配置入口：`js/config/performance.js`；诊断数据：`require('./js/game/fx/approved-debuffs.js').stats()`。

## 验证结果与边界

- 真实状态合成代码配合画布适配器：60 只怪物、18 种精灵裁帧、灼烧/中毒/冻结/麻痹叠加，36 帧用例约 412ms → 60ms；画布创建 366 → 54，像素读回 36 → 18。数值随电脑负载变化；不包含真实 GPU 上传耗时，不能换算成手机温度或帧率提升。
- 再运行 360 帧：每帧合成数不超过 1，缓存最多 160 张，轮廓和队列均不越界；重开清零；不支持像素读回时只失败尝试一次。
- 验证怪物状态数据未被表现层修改，受击状态只绘制一次，图集尺寸、透明通道、裁帧及范围缩放正确。
- 启动及五个分页、毒池伤害/命中反馈、炮台生命周期、Combo×3 与四连技能回归通过。此次未修改攻击力、攻速、伤害、掉落、出怪或游戏帧率。
- 仍需真机比较同一手机、同一画质和倍速，在 20/30/40 波的帧耗时、内存和温度。尚未取得真机性能采样，不能断言已经消除全部发热来源。

## 后续采样重点

高像素比屏幕的主画布像素填充量、后期存活怪物数量和叠加地面数量仍会增加负载。当前未直接降低分辨率或帧率，先验证上述热点修复；如仍发热，再根据真机采样决定是否增加画质/省电选项。
